Praktische Hinweise

AI-Tools effektiv nutzen

Kontextfenster

Jedes Modell hat ein begrenztes Gedächtnis pro Session. Wenn es voll ist, werden frühere Anweisungen verdrängt — die Qualität sinkt ohne offensichtlichen Grund.

ModellKontextFüllt sich schnell
Claude Sonnet / Opus200.000 TokensClaude Code: ja
GPT-4o / GPT-5128.000 Tokensmittel
Gemini 2.5 Pro1.000.000 Tokensnein

In Claude Code: nach jeder abgeschlossenen Aufgabe /clear ausführen. CLAUDE.md wird automatisch neu geladen — die Projektregeln gehen nicht verloren.

Weitere Hinweise

Cursor: Modell explizit wählen
Auto-Modus wählt das Modell ohne Rückmeldung. Claude Sonnet oder GPT-4o manuell setzen.
Prompt-Qualität bestimmt Output-Qualität
Ein vager Prompt produziert einen vagen Test. Schritte konkret beschreiben, Erwartungen benennen.
Generierten Code immer prüfen
AI macht Fehler. Den Test lesen, den Trace öffnen, die Assertions verstehen bevor man weitergeht.
Claude Code vs. Cursor: derselbe Output
Gleiche Regeldatei, gleiches Modell — gleiche Testqualität. Der Unterschied ist wie viele Schritte ihr manuell macht.

Rules

Konventionen für alle Tools

Jedes Tool liest beim Projektstart eine Konfigurationsdatei automatisch. Konventionen werden einmal definiert und gelten für jede Session.

playwright-workshop/
├── CLAUDE.md← Claude Code
├── AGENTS.md← Codex
├── .cursorrules← Cursor
├── .github/
│ └── copilot-instructions.md← Copilot
└── tests/
Claude CodeCLAUDE.md auto ↗
Cursor.cursorrules / .cursor/rules/ auto ↗
GitHub Copilot.github/copilot-instructions.md auto ↗
CodexAGENTS.md auto ↗
ChatGPTmanuell in den Chat einfügen manuell

Inhalt der Regeldateien in diesem Repo:

# Sprache
test.step() Namen auf Deutsch
Aktionen: "Der Benutzer..."

# Struktur
Aktion → Ergebnis, immer in Paaren
niemals zwei Aktionen hintereinander

# Locators
[data-test="..."] ← erste Wahl
getByRole, getByPlaceholder ← Fallback
CSS-Klassen, XPath ← nie

Alle vier Dateien enthalten denselben Inhalt — unterschiedlich formatiert für jedes Tool. Repo klonen reicht.

Skills — woher sie kommen

Selbst schreiben oder fertige nutzen

Eigene Skills schreiben

Ihr beschreibt einen wiederkehrenden Workflow — Claude Code erstellt die SKILL.md-Datei selbst. Ihr testet sie, verbessert sie wenn nötig.

# So entsteht eine Skill
$ claude
"Erstelle eine Skill 'login-helper' die
 einen Login-Block für saucedemo
 in jeden Test einfügt."

→ Claude Code erstellt die Datei:
.claude/skills/login-helper/SKILL.md

Faustregel: Wenn du denselben Prompt mehr als dreimal eintippst — mach eine Skill daraus.

Vorhandene Skills installieren

Die Community veröffentlicht Skills für gängige Frameworks — auch für Playwright.

Vorsicht bei fremden Skills

Skills sind Code

Eine SKILL.md-Datei ist eine Anweisung an einen autonomen Agenten. Bevor ihr eine Skill aus dem Internet installiert — lest was drin steht.

Was schiefgehen kann

Konflikt mit euren Regeln
Eine fremde Skill kann CSS-Selektoren erzwingen — und damit eure Konvention überschreiben.
Veraltete Patterns
Skills von 2024 nutzen oft Playwright-APIs die heute deprecated sind.
Unklare Bash-Befehle
Skills können Shell-Commands ausführen. Ein unbedachter rm -rf in einer Anweisung — und die Files sind weg.
Daten-Exfiltration
Theoretisch kann eine Skill Claude anweisen Projektinhalte an eine externe URL zu schicken.

Checkliste vor Installation

SKILL.md selbst lesen
Im GitHub-Repo öffnen. Die Datei ist Markdown — lesbar in 2 Minuten.
Quelle prüfen
Bekannter Maintainer? Aktiv gepflegt? GitHub Stars · letzter Commit · Issues.
Bash-Commands suchen
Strg+F nach $, curl, rm, npm install. Verstehst du jeden Befehl?
In Test-Repo testen
Erst in einem leeren Projekt ausprobieren — nicht direkt im produktiven Repo.
Plan Mode nutzen
Erste Ausführung in Claude Code's Plan Mode — Aktionen sichtbar, bevor sie passieren.

Output-Vergleich

Ohne Rules vs. Mit Rules

Ohne Rules 
// Generierter Output — kein AGENTS.md,
// kein .cursorrules

test('checkout flow', async ({ page }) => {
  await page.goto('https://www.saucedemo.com');
  await page.fill('#user-name', 'standard_user');
  await page.fill('#password', 'secret_sauce');
  await page.click('#login-button');
  await page.selectOption(
    '.product_sort_container', 'lohi');
  await page.click('.btn_inventory');
  await page.click('.shopping_cart_link');
  await page.click('#checkout');
  await page.fill('#first-name', 'Test');
  await page.fill('#last-name', 'User');
  await page.fill('#postal-code', '12345');
  await page.click('#continue');
  await page.click('#finish');
  expect(await page.locator(
    '.complete-header').textContent())
    .toBe('Thank you for your order!');
});
✗CSS-Klassen — brechen mit problem_user
✗Keine test.step() — Trace unlesbar
✗Eine Assertion am Ende — kein Zwischencheck
✗Keine deutsche Benennung
Mit Rules 
// Gleicher Prompt — mit AGENTS.md/.cursorrules

test('Checkout-Flow', async ({ page }) => {

  await test.step(
    'Der Benutzer navigiert zu saucedemo.com.',
    async () => {
      await page.goto('https://www.saucedemo.com');
  });
  await test.step(
    'Die Login-Seite wird angezeigt.',
    async () => {
      await expect(page.locator(
        '[data-test="username"]')).toBeVisible();
  });

  await test.step(
    'Der Benutzer meldet sich an.',
    async () => {
      await page.locator(
        '[data-test="username"]').fill('standard_user');
      await page.locator(
        '[data-test="password"]').fill('secret_sauce');
      await page.locator(
        '[data-test="login-button"]').click();
  });
  await test.step(
    'Die Produktseite wird angezeigt.',
    async () => {
      await expect(page).toHaveURL(/inventory/);
  });
  // ... weitere Schritt-Paare
  await test.step(
    'Die Bestätigung zeigt "Thank you for your order!".',
    async () => {
      await expect(page.locator(
        '[data-test="complete-header"]'))
        .toHaveText('Thank you for your order!');
  });
});
✓data-test Attribute — stabil über alle User
✓test.step() Paare — Trace lesbar
✓Assertion nach jedem Schritt
✓Deutsche Schritt-Namen
